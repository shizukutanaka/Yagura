# 複数リポジトリ再計測 — 単一リポジトリ結論の検証(v1.82.0)

`docs/PRODUCT_ASSESSMENT.md` が第 1 位の未解決項目として挙げた
「複数リポジトリでの再計測」を実施した。**結論のいくつかは覆った。**

## 対象

| repo | commits(Go 履歴) | Go files | 期間 |
|---|---|---|---|
| yagura | 162 | 353 | ~2 か月 |
| groupcache | 37 | 16 | 11 年 |
| gorilla/mux | 188 | 17 | 11.7 年 |
| sirupsen/logrus | 627 | 53 | **12.5 年** |

すべて `internal/churn` + `internal/walkforward` + `internal/cochange` の
既存コードパス(MCP tool と同一)で測定。

---

## 発見 1 — **yagura 自身の数値は外れ値だった**

walk-forward の lift(3 fold、既定設定):

| repo | size_loc | churn_count | complexity | relative_churn | baseline |
|---|---|---|---|---|---|
| **yagura** | **6.27** | **7.34** | 2.99 | 2.49 | 0.100 |
| groupcache | 2.84 | 0.00 | 0.00 | 0.00 | 0.214 |
| mux | 1.30 | 1.30 | 1.30 | 0.83 | 0.794 |
| logrus | 1.53 | 1.53 | 1.53 | 1.53 | 0.656 |

**yagura の 6-7× は、実プロジェクトの 1.3-2.8× に対して 4-5 倍高い。**
原因は yagura の履歴構造そのもの——リリース儀式で同じ 4 ファイルが全 commit に現れ、
それが同時に「最大」かつ「最頻変更」でもあるため、どのランキングも当たりやすい。

**含意**: v0.119-0.128 に記録した lift 値は、他リポジトリの期待値ではない。
「単一リポジトリの 1 観測点」という但し書きは形式的な保険ではなく、**実際に効いていた**。

## 発見 2 — **precision@K は小規模リポジトリで飽和する(新規の方法論的限界)**

mux と logrus では **4 つの scorer が完全に同点**、precision = 1.000。
理由は baseline(陽性率)が 0.656-0.794 と高いこと——ファイル数が 17/53 と少なく、
ラベル窓でほぼ全ファイルが fix に触れられるため、**どう並べても上位 K は全部当たる**。

つまりこの条件下では **precision@K は scorer を識別する能力を持たない**。
これは v0.125.0 以降ずっと使ってきた指標の、これまで気づいていなかった限界である。
lift が 1.0 に貼り付いた数値を「差が無い」と読むのは誤りで、正しくは
**「この指標ではこの規模で差を検出できない」**。

## 発見 3 — **v0.128.0 の change coupling 結論はリポジトリ固有だった**

「掘り出した結合は頻度ベースラインにほぼ勝てない」という v0.128.0 の結論:

| repo | k=1 (confidence) | k=1 (lift-rank) | k=3 (confidence) | coverage |
|---|---|---|---|---|
| yagura | 0.96(**負け**) | 1.13 | 1.94 | 0.65 |
| mux | 1.00(同点) | 0.55 | 1.00 | 0.61 |
| **logrus** | **1.32(勝ち)** | 1.29 | **1.27(勝ち)** | 0.35 |
| groupcache | 既定しきい値で規則 0 件(invalid) | — | — | — |

**実履歴のある logrus では coupling が baseline に勝つ。** yagura で負けていたのは、
リリース儀式が頻度ベースラインを異常に強くしていたため(v0.128.0 自身がその機序を
指摘していたが、「他repoでは違う」までは示せていなかった)。

## 発見 4 — sliding window: **expanding が単調に勝つ**(ただし交絡あり)

v0.127.0 は「2 か月の履歴では 1 年規模の効果を検証できない」と null result を記録した。
12.5 年の logrus で測り直した結果(churn_count lift):

| window | logrus (4560 日) | mux (4258 日) |
|---|---|---|
| expanding | **1.53** | **1.30** |
| 10 年 | 1.53 | 1.30 |
| 2 年 | 1.47 | 1.23 |
| 1 年 | 1.34 | 1.08 |
| 180 日 | 1.25 | 1.00 |
| 90 日 | 1.23 | 1.00 |

**両リポジトリで単調に低下する。** 窓を短くするほど悪化し、expanding が最良。

**これは McIntosh & Kamei を反証しない。** 窓を縮めると
「古いデータを捨てる(鮮度↑)」と「データ量が減る(統計↓)」が同時に起きる
(logrus の feature 窓は 468 → 22 commits まで縮む)。本プロトコルは 2 つの効果を
分離できないので、言えるのは **「この実装の sliding window は、試した 3 リポジトリの
どれでも一度も役に立たなかった」** ということだけである。既定(expanding)は正しい。

なお窓を縮めると baseline が上昇する(logrus 0.656 → 0.828)。行集合が痩せて
高頻度ファイルだけが残るためで、v0.127.0 が指摘した母集団シフトがここでも起きている。

---

## この再計測が変えたこと

1. **CHANGELOG の lift 値は「yagura 固有の値」と読むべき**(発見 1)。
2. **precision@K には規模依存の識別限界がある**(発見 2、新規)。
3. **coupling は使い物になる可能性がある** — 少なくとも logrus では baseline に勝つ(発見 3)。
4. **sliding window は既定にしない** — 3 リポジトリで一度も勝たなかった(発見 4)。

## 再現方法

```bash
git clone https://github.com/sirupsen/logrus /tmp/logrus
yagura register --slug logrus --local-path /tmp/logrus ...
# MCP: yagura_process_risk / yagura_change_coupling を slug 指定で呼ぶ
```

測定は本リポジトリの既存コードパスのみを使用しており、専用の実験コードは残していない
(一時ハーネスは意図的に削除した——再現は上記の公開手順で足りる)。
